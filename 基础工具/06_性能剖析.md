## 🎯 这一份解决什么问题

**让你在回答"为什么慢"时，有证据，而不是猜。**

大部分人优化性能的方式是**凭直觉改代码**，改完跑一下发现没变快，或者变慢了。

**性能剖析（profiling）= 让程序自己告诉你时间花在哪。**

这也正是 Day 56 用 godbolt 看汇编的延续：**godbolt 看的是"这段代码编译成什么"，profiling 看的是"运行时时间花在哪"。**

## 二、三个层次的手段

**别一上来就学最复杂的。** 按这个顺序用：

| 层次 | 手段 | 什么时候用 |
|---|---|---|
| **① 计时** | `std::chrono`、`time` 命令 | 想知道**整体**多快 |
| **② 采样** | `perf`、火焰图 | 想知道**时间花在哪些函数** |
| **③ 插桩** | `valgrind --tool=callgrind` | 想知道**精确调用次数和占比** |

**Day 55 的 benchmark 属于第 ① 层**——已经够回答"我的 MyVector 比 std::vector 慢多少"。

第 ②③ 层回答的是更深的问题：**慢在哪。**

## 三、① 计时（你现在就能用）

```bash
# 最简单：用 time 命令
time ./build/app

# 输出：
# real    0m1.234s      ← 墙上时间（你感受到的）
# user    0m1.100s      ← 用户态 CPU 时间
# sys     0m0.134s      ← 内核态 CPU 时间
```

**三个时间的意义**：

| 字段 | 含义 | 什么时候关注 |
|---|---|---|
| `real` | 实际流逝的时间 | 用户体验 |
| `user` | 你的代码用了多少 CPU | 计算密集 |
| `sys` | 系统调用用了多少 CPU | IO 密集 |

**如果 `real` 远大于 `user + sys`** → 在等 IO（磁盘、网络、锁）。

### C++ 里精确计时

```cpp
#include <chrono>

auto t0 = std::chrono::high_resolution_clock::now();
// ... 被测代码 ...
auto t1 = std::chrono::high_resolution_clock::now();

double ms = std::chrono::duration<double, std::milli>(t1 - t0).count();
std::cout << ms << " ms\n";
```

**这就是 Day 55 要写的东西。**

## 四、② perf —— 采样剖析

### 原理

**perf 每秒钟中断程序几千次，记录"当时正在执行哪个函数"。**

跑一段时间后，统计哪个函数被采样到的次数最多 → 那就是热点。

**优点**：开销极小（1–5%），可以直接跑真实程序。
**缺点**：是统计采样，不是精确计数。

### 基本用法

```bash
# 记录
perf record -g ./build/app        # -g = 记录调用栈

# 查看报告（文本）
perf report

# 查看报告（直接打印）
perf report --stdio | head -40
```

输出长这样：

```
   Overhead  Command  Shared Object      Symbol
   -------  .......  .................  ...........................
     42.31%  app      app                [.] MyVector<int>::push_back
     28.07%  app      app                [.] MyVector<int>::reallocate
     12.55%  app      libc.so.6          [.] memcpy
      8.20%  app      app                [.] main
```

**`Overhead` 就是"这个函数占了多少时间"。** 一目了然。

### 常用参数

| 参数 | 作用 |
|---|---|
| `perf record -g` | 记录调用栈 |
| `perf record -F 999` | 采样频率（默认约 4000 Hz） |
| `perf stat ./app` | **不采样**，只看总览（CPU 周期、cache miss、分支预测失败） |
| `perf top` | 实时看系统热点（类似 top） |
| `perf report --stdio` | 文本格式输出 |

### `perf stat` 特别有用

```bash
perf stat ./build/app
```

```
    1,234,567,890      cycles
      987,654,321      instructions        #  ← 每周期指令数 = IPC
      123,456,789      cache-misses        #  ← 缓存未命中
      456,789,012      branch-misses
```

**IPC（Instructions Per Cycle）< 1** 通常说明在等内存（cache miss 高）。
**这正是 Day 03 讲的体系结构知识落地的地方。**

## 五、火焰图（Flame Graph）

**perf 的文本报告不够直观，火焰图是可视化版本。**

### 生成步骤

```bash
# 1. 记录
perf record -g ./build/app

# 2. 导出
perf script > out.perf

# 3. 用火焰图脚本转换成 SVG
git clone https://github.com/brendangregg/FlameGraph
./FlameGraph/stackcollapse-perf.pl out.perf > out.folded
./FlameGraph/flamegraph.pl out.folded > flamegraph.svg
```

**用浏览器打开 `flamegraph.svg`。**

### 怎么看

```
┌──────────────────────────────────────────────────┐
│                     main                          │  ← 最底下是入口
├────────────────────┬─────────────────────────────┤
│   push_back        │      process_data           │
├──────────┬─────────┼──────────────┬──────────────┤
│reallocate│ memcpy  │   parse      │   compute    │  ← 越宽 = 越耗时
└──────────┴─────────┴──────────────┴──────────────┘
```

**三条规则**：

1. **宽度 = 耗时占比**（不是高度！）
2. **上下 = 调用关系**（下面是调用者，上面是被调用者）
3. **找最宽的"平顶"** —— 那是热点

**别被高度迷惑**：一个很窄但很高的塔，不代表它耗时间。**只看宽度。**

## 六、③ callgrind —— 精确计数

**valgrind 不只能查内存，还能查性能。**

```bash
valgrind --tool=callgrind ./build/app
```

生成 `callgrind.out.<pid>`，然后用可视化工具看：

```bash
# 安装
sudo apt install kcachegrind

# 打开
kcachegrind callgrind.out.12345
```

**特点**：

| | perf | callgrind |
|---|---|---|
| 原理 | 采样 | **精确插桩** |
| 速度 | 快（1–5% 开销） | **慢 20–100 倍** |
| 精度 | 统计 | **精确到每条指令** |
| 缓存模拟 | 无 | **有**（能看 cache miss） |

**什么时候用 callgrind**：perf 定位到大方向后，想深入看某个函数内的精确耗时分布。

## 七、⚠️ 三个必须知道的坑

### 坑 1：一定要用 Release 编译

**Debug（`-O0`）的性能数据毫无意义。**

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
```

`-O0` 下每个变量都从内存读写，函数不内联，**代码结构和你写的几乎一一对应**——但真实运行时不是这样。

### 坑 2：编译器会优化掉你的代码

```cpp
// ❌ 结果没被使用，编译器直接删掉整个循环
for (int i = 0; i < 1000000; ++i) sum += i;

// ✅ 用 volatile 或打印结果，防止被优化掉
volatile int sink = sum;
```

**Day 55 的 benchmark 里 `volatile long long sum` 就是干这个的。**

### 坑 3：单次测量噪声很大

**跑一次的数字不可信。** 至少跑 3–5 次取中位数，并且：

- 关掉其他占 CPU 的程序
- 第一次跑通常偏慢（冷启动、cache 冷）——**丢掉第一次**
- 用固定随机种子，保证每次输入一样

## 🤔 卡住了怎么办

| 症状 | 解法 |
|---|---|
| `perf: command not found` | 装 `linux-tools` 包；或改用 WSL |
| `perf` 报权限错误 | `sudo perf record ...`；或调 `perf_event_paranoid` |
| WSL 里 perf 不工作 | WSL2 支持有限，`perf stat` 通常可用，`perf record` 可能失败 |
| 火焰图全是 `[unknown]` | 编译时没加 `-g` |
| 数字每次差很多 | 正常。多跑几次取中位数，丢第一次 |
